## The window-switching tax

Working with a coding agent means running two systems of record at once. The agent has its notes. You have your to-do app. Keeping them in sync is manual, and it is on you.

You hand the agent a task, then wait for it to finish. It finishes. You switch to your to-do app, find the row, tick it off. An idea lands mid-run — switch back, type it, switch away. The more work in flight, the more of your attention that loop eats.

**farol removes the second window.** Your agent writes to the same store your terminal is already showing you. Progress moves on the row you are looking at. New tasks appear in the tree. Completed tasks cascade into the Complete section. Nothing to reconcile.

## What each side gets

One store, two audiences. Neither surface is a wrapper around the other.

### For you, at the keyboard

- **See which task is moving, not just that something changed.** When an agent claims a row, its tag appears on that row. Two agents at once are two visible spinners.
- **A tree, not a flat list.** Nest to any depth; a parent's percentage can derive from its children, and completing the last child completes the parent.
- **One cursor across everything.** Vim or arrows navigate the tree; `space` toggles complete (cascading down); `/` filters the current list; `F` searches every list at once.
- **Inline everything.** New tasks are spliced into the tree with `n`. `[` and `]` change the level while you type. The Details modal opens over the tree with `enter` and closes with `esc`.

### For your agent, at the CLI

- **`farol skill` prints the whole reference.** Pipe it into your agent's context and it knows the identity contract, the working loop, the ownership gate, and the traps it hits on its first run.
- **`farol inbox` is the start-of-session context call.** One read returns the agent's own list plus every other list in the store, with top pending tasks in each.
- **`farol next <list>` is the work queue.** It picks the top-priority eligible task, assigns it to the calling agent atomically, and returns it as JSON.
- **Assignment reserves the whole subtree.** No other agent can take an ancestor or a descendant of a claimed task, so two agents working the same list never do the same work twice.
- **Every `--json` call prints exactly one JSON value on stdout** — the payload on success, `{"error": "..."}` on failure. Exit codes are stable: `0` success, `1` domain failure, `2` usage.
- **No MCP server.** farol shipped one and retired it. Running a subprocess and a JSON-RPC handshake so an agent can invoke commands it can already invoke is a moving part with nothing to show for it. The CLI is the API.

## Also, without ceremony

Fourteen themes with live preview · vim and arrow navigation · four-level priority · notes, comments, and file attachments per task · a `--since` change feed for polling agents · versioned export and import · one static binary, no daemon, no config required.
